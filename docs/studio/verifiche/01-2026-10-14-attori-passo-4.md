## Domanda 1 — Il viaggio della password (punto di vista di una cosa)

**Domanda.** Sei la password del database, scritta nel file `.env`. Racconta il tuo viaggio: chi ti legge e quando, chi ti trasporta e dove arrivi, chi ti usa per controllare che qualcuno abbia il diritto di entrare. C'è un momento dopo il quale, se Nicholas ti cambia nel `.env`, nessuno se ne accorge più: quale, e perché?

**Risposta di Nicholas:**
> Credo che direttamente da .env non mi legga e non debba leggermi nessuno. Per quanto riguarda compose per esempio, il file .yaml fa da tramite anche grazie ai placeholders. Stesso discorso per Spring tramite application.properties.
>
> Questo risponde anche alla domanda due sul chi mi trasporta e dove arrivo.
>
> Nel caso di una pw di Postgres controllerà la correttezza il container Docker che runna l'immagine di Postgres.
>
> Per quanto riguarda l'ultima domanda, se non ricordo male, sempre con Docker, il file .yaml non viene letto ogni volta. Quindi se abbiamo un container già creato e cambiamo una pw in .env il cambiamento non viene apportato a meno che il container non venga ricreato da capo.

**Correzione.**

✅ Nei file versionati la password non compare mai: `.yml` e `application.properties` contengono solo riferimenti (`${POSTGRES_PASSWORD}`).

❌ **"Direttamente dal .env non mi legge nessuno"**: al contrario, il `.env` è letto direttamente da **due programmi**: Docker Compose (con `--env-file .env`) e Spring Boot (con `spring.config.import`). Il `.yml` e `application.properties` non leggono niente: sono file, passivi come il `.env`. **Gli attori sono i programmi, i file sono istruzioni.**

```
                ┌─► Compose ──► ambiente del container ──► script di inizializzazione di Postgres
.env ── letto da┤                                          (crea l'utente, salva l'IMPRONTA della password nel volume)
                └─► Spring Boot ──► spring.datasource.password ──► HikariCP ──► driver JDBC ──► rete ──► server PostgreSQL
                                                                                                        (confronta con l'impronta)
```

🟡 **"Controlla il container"**: il container è solo la scatola isolata; Docker non sa niente di password. Controlla il **processo server PostgreSQL**, confrontando con l'**impronta** (*hash*) salvata nei file del database, cioè **nel volume**, non con la variabile d'ambiente.

❌ **"Ricreando il container la password cambia"**: Compose rilegge `.yml` e `.env` a **ogni** comando; se la configurazione cambia, `up` ricrea il container. Ma lo script di inizializzazione usa `POSTGRES_PASSWORD` **solo se la cartella dei dati è vuota**. Il momento giusto è il **primo avvio su volume vuoto**: dopo, il container ha la password nuova nell'ambiente ma è ignorata; Spring legge la nuova dal `.env` e ottiene `password authentication failed`. Si risolve con `ALTER USER ... PASSWORD` (conserva i dati) o `down -v` (cancella tutto).

**Da ripassare:** guida 02, 1.6.

## Domanda 2 — Dall'avvio di `mvnw` a `Started` (punto di vista di un processo)

**Domanda.** Sei il processo Java che parte quando Nicholas, in `backend/`, scrive `.\mvnw.cmd spring-boot:run`. Racconta in ordine cosa succede fino a `Started BookingApplication`, e chi lavora a ogni passaggio. Conta l'ordine, e perché alcuni passaggi devono venire prima di altri.

**Risposta di Nicholas:**
> 1) Dal pom.xml Spring Boot trova versione di Java
> 2) Il compilatore del Java development kit compila
> 3) Spring Boot legge application.properties grazie a spring.config.import
> 4) HikariCP apre il pool con le connessioni grazie a JDBC
> 5) Lo schema viene toccato grazie a Flyway che applica le migrazioni
> 6) Lo schema viene controlalto da Hibernate settando ddl-auto su validate
> 7) La porta 8080 viene aperta dal server Tomcat

**Correzione.**

❌ **Punto 1**: in quel momento Spring Boot non esiste ancora. `mvnw.cmd` trova Java tramite `JAVA_HOME` e avvia Maven; Maven legge il `pom.xml`. `java.version` nel pom non dice **dove** trovare Java, ma **per quale versione** compilare.

| Domanda | Chi risponde |
|---|---|
| Con quale Java **eseguo** Maven? | `JAVA_HOME` |
| Per quale versione **compilo**? | `java.version` nel pom |

🟡 **Punto 2**: `javac` compila, ma lo chiama **Maven** (plugin del compilatore), dopo aver risolto le dipendenze da `.m2`. Poi il goal `spring-boot:run` **avvia un nuovo processo Java**: è lì che nasce il processo della domanda.

🟡 **Punto 3**: rapporto invertito. Spring legge `application.properties` da solo, per convenzione; è `spring.config.import`, scritto **dentro** quel file, a fargli leggere anche il `.env`.

❌ **Manca il regista**: tra 3 e 4, `ApplicationContext`, *component scan* e **auto-configurazione**, che valuta le condizioni e **decide** di creare i bean di Hikari, Flyway e Hibernate.

✅ **Punti 4–7**: ordine corretto. Ma Hibernate non *imposta* `ddl-auto`, lo legge; e mancava il **perché**: Flyway deve precedere Hibernate perché la validazione controlla tabelle che devono già esistere, e Spring Boot lo garantisce rendendo il bean di Hibernate dipendente da quello di Flyway. Tomcat parte per ultimo: la porta si apre solo quando il database è pronto e verificato.

```
mvnw (JAVA_HOME) → Maven (pom, dipendenze, javac) → spring-boot:run avvia il processo
→ Spring legge la configurazione (application.properties → import del .env)
→ ApplicationContext + component scan + auto-configurazione (decide quali bean creare)
→ HikariCP → Flyway migra → Hibernate valida → Tomcat apre la 8080 → "Started"
```

**Da ripassare:** guida 01, 2.6, 3.7, 4.3, 4.5; guida 03, domanda 5.

## Domanda 3 — Giulia clona il repository (punto di vista di una persona)

**Domanda.** Giulia ha un portatile Windows nuovo con solo Git, e clona il repository. (1) Cosa deve installare, e cosa non deve installare pur essendo necessario? (2) Quale file che hai tu lei non trova, e come sa cosa metterci? (3) Quali comandi lancia, in che ordine, e cosa succede se inverte i primi due?

**Risposta di Nicholas:**
> 1) La JDK corretta, un IDE su cui aprire il progetto e installare i plugin di Spring Boot. Nel caso di questo specifico progetto anche Docker Desktop (e di conseguenza WLS2). Non credo sia necessario che installi maven poichè se non presente viene installato in automatico, relativamente alla versione Java, se non è presente
> 2) Si tratta del file .env. Può sapere cosa metterci dentro guardando al file .env.example
> 3) Deve lanciare prima il comando per Docker Compose avviando il database, poi il comando mvnw.cmd per la compilazione (build) e infine spring-boot:run per avviare un nuovo processo

**Correzione.**

✅ JDK 21 e Docker Desktop (con WSL2); aggiungere `JAVA_HOME` configurato.
🟡 IDE e plugin: comodi ma non necessari, tutto funziona da terminale.
🟡 Maven: giusto non installarlo, ma la versione **non dipende da Java**: è fissata in `.mvn/wrapper/maven-wrapper.properties` e lo script la **scarica** in `.m2\wrapper`.
❌ Mancava **PostgreSQL**: non si installa, arriva come immagine Docker. Nemmeno le librerie: le scarica Maven.

| Da installare | Arriva da solo |
|---|---|
| Git, JDK 21 (+ `JAVA_HOME`), Docker Desktop | Maven (Wrapper), librerie (Maven Central), PostgreSQL (Docker Hub) |

✅ Il `.env`, da `.env.example`; non è nel repository per via di `.gitignore`. Giulia sceglie i **suoi** valori, **prima del primo `up`** (collegamento con la domanda 1).

🟡 Il primo comando è creare il `.env`. Compilazione e avvio non sono comandi separati: `.\mvnw.cmd spring-boot:run` compila e avvia.

```
Copy-Item .env.example .env        (e scelgo i miei valori)
docker compose -f infra/docker-compose.dev.yml --env-file .env up -d
cd backend; .\mvnw.cmd spring-boot:run
```

❌ Non ha risposto a "cosa succede se inverte": Spring **non aspetta** il database; Hikari e Flyway non trovano nessuno su `localhost:5432`, l'avvio fallisce con `Connection refused` e il processo termina.

**Da ripassare:** guida 01, 3.8; guida 02, Parte 4.

## Domanda 4 — `Connection refused` dopo il riavvio (detective)

**Domanda.** Lunedì riaccendi il computer, lanci `.\mvnw.cmd spring-boot:run` senza aver toccato file, e ottieni `Connection to localhost:5432 refused`. (1) Gli anelli della catena da Spring a PostgreSQL. (2) Il colpevole più probabile e perché. (3) Con quale comando verifichi e con quale risolvi. (4) I dati di venerdì ci sono ancora?

**Risposta di Nicholas:**
> 1) Spring Boot ──► spring.datasource.password ──► HikariCP ──► driver JDBC ──► rete ──► server PostgreSQL
> 2) A me verrebbe in mente il volume del container di Docker di non correttamente montato o nominato che allo spegnimento del PC crea problemi, ma non credo che si risolva nell'errore Connection to localhost:5432 refused

**Correzione.**

❌ **Catena**: è quella della password (domanda 1), non della connessione. `refused` avviene **prima** di qualsiasi password. Mancavano gli anelli centrali:

```
Spring → HikariCP → driver JDBC → localhost:5432 (Windows)
       → Docker Desktop (pubblica la porta) → macchina virtuale WSL2 → container → processo PostgreSQL
```

✅ **Buon istinto** nello scartare il volume: un problema di volume non dà `refused`.

| Messaggio | Livello | Dove guardi |
|---|---|---|
| `Connection refused` | Nessuno in ascolto sulla porta | I processi: Docker è acceso? Il container gira? |
| `password authentication failed` | Qualcuno risponde, ma non ti riconosce | Le credenziali |
| `database "..." does not exist` | Ti riconosce, ma i dati non sono quelli attesi | Il volume e il `.env` |

❌ **Colpevole** (non individuato): **i file sopravvivono al riavvio, i processi no.** Docker Desktop non partito con Windows e/o container rimasto *Exited* (nessuna regola `restart:` nel `.yml`).

❌ **Verifica e soluzione** (non risposto): `docker compose -f infra/docker-compose.dev.yml --env-file .env ps -a` → errore su `dockerDesktopLinuxEngine` = Docker spento; stato `Exited` = container spento. Si risolve avviando Docker Desktop e `up -d`. Opzionale: `restart: unless-stopped`.

❌ **Dati** (non risposto): ci sono ancora. Il named volume vive indipendentemente dal container, sul disco virtuale di WSL2, ed era stato verificato con la prova `down`/`up`. Si perde solo con `down -v` o cancellandolo.

**Da ripassare:** guida 02, 1.4, 1.5, Parte 4 (errori tipici).

## Domanda 5 — Hibernate e la migrazione dimenticata (cosa succede se)

**Domanda.** Sei Hibernate con `ddl-auto=validate`. Nicholas aggiunge a `AppUser` il campo `lastLoginAt` ma dimentica la migrazione. (1) Cosa fai all'avvio? (2) Se Nicholas passa a `update`, cosa succede nel test con Testcontainers e in produzione, e perché sul suo computer va tutto bene? (3) Ti accorgi se manca il vincolo check sul ruolo?

**Risposta di Nicholas:**
> 1) Controllo che per ogni entità esistano le tabelle e le colonne, con tipi compatibili. Se qualcosa manca, l'applicazione non parte. Nicholas vede un errore di mancata corrispondenza tra entità e tabella a database
> 2) Con update creo una colonna nuova e lascio la vecchia con i dati dentro. Non cancello, non rinomino, non sposto dati. Quindi credo che le risposte alle domande abbiano a che fare con questo
> 3) Con validate non controllo vincoli, indici, valori di default, né colonne in più nel database

**Correzione.** Le risposte 1 e 3 sono corrette ma quasi testuali dalla guida; la 2 è **la frase della guida** e non ragiona sullo scenario.

✅ **1.** L'errore sarà simile a `Schema-validation: missing column [last_login_at] in table [app_user]`: `lastLoginAt` diventa `last_login_at` (conversione *camelCase* → *snake_case*). L'errore si vede subito, in locale.

❌ **2.** Il campo è nuovo, non c'è niente da rinominare: `update` **aggiunge** la colonna al database su cui gira.
- Sul suo computer va bene perché **Hibernate ha corretto da solo il suo database**.
- Nel test: *correzione della premessa della domanda* — se il test usa la stessa configurazione, `update` agisce anche lì e **il test passa**. `update` nasconde il problema ovunque.
- In produzione: Hibernate esegue un `ALTER TABLE` non scritto da nessuna parte, sui dati veri; e l'utente del backend deve avere permessi di modifica dello schema che non dovrebbe avere (minimo privilegio).
- Il guaio arriva quando si scrive la migrazione: funziona sul database vuoto dei test, **fallisce** in locale e in produzione perché la colonna esiste già.

Con `update` ogni database ha la sua storia; con `validate` la storia è una sola, nelle migrazioni.

🟡 **3.** Manca il perché: Hibernate confronta quello che **sa dalle entità** con il database; nell'entità niente dice che debba esistere un check, quindi non può accorgersi che manca. Lo garantiscono la migrazione V1 e il **test di integrazione** che prova a salvare un ruolo non ammesso.

**Da ripassare:** guida 03, domanda 4.

## Domanda 6 — Il server di produzione (punto di vista di un luogo)

**Domanda.** Sei il server Hetzner, con i container `backend` (stesso jar e stesso `application.properties`) e `postgres`. (1) Cosa succede con `spring.config.import=optional:...`, perché non si blocca, da dove arrivano utente e password? (2) Perché `localhost` non funziona, cosa vale `POSTGRES_HOST`, chi lo fa funzionare? (3) Il servizio `postgres` ha `ports:`? Cosa c'entra il firewall?

**Risposta di Nicholas:**
> 1) Il file .env non c'è, quindi ti direi da variabili d'ambiente che devono essere settate nel container Docker di backend?
> 2) localhost non funziona più perchè non si riferisce più alla macchina locale come faceva prima. POSTGRES_HOST deve valere l'indirizzo IP della macchina su cui gira. Hetzner lo fa funzionare
> 3) Se non sbaglio non deve averla perchè bypassa anche ufw. Così ci si avvale di un reverse proxy come Caddy

**Correzione.**

✅ **1.** `optional:` salta il file mancante. Le variabili d'ambiente del container `backend` le mette **Compose**, che sul server legge il **suo** `.env`; i placeholder le trovano perché Spring cerca in tutte le fonti e le variabili d'ambiente hanno la precedenza più alta.

❌ **2.** Dentro il container `backend`, `localhost` è **il container stesso**. L'IP del server richiederebbe di pubblicare la porta del database, contraddicendo la risposta 3. Si usa **`POSTGRES_HOST=postgres`**, il nome del servizio: Compose crea una rete interna e **Docker** fa da DNS, traducendo il nome nell'indirizzo del container (che cambia a ogni ricreazione, il nome no). Hetzner fornisce solo la macchina.

🟡 **3.** Niente `ports:`, e il motivo `ufw` è giusto. Ma Caddy non c'entra con il database: gestisce solo il traffico web (80/443). Il database non ha bisogno di tramiti perché nessuno da fuori deve raggiungerlo. Per guardare i dati: SSH + `docker exec ... psql`.

```
Internet ──► :443 Caddy ──► backend ──(rete interna, "postgres:5432")──► postgres
             unica porta pubblicata          nessuna porta pubblicata ──┘
```

**Da ripassare:** guida 02, 1.5 e domanda 4; guida 03, 1.5 e domanda 3.
